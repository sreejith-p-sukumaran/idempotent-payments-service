# Idempotent Payments Service — Design

A small Spring Boot (Kotlin) service exposing one meaningful endpoint:

```
POST /payments
Idempotency-Key: <client-generated-key>
```

The guarantee: **retrying the same request never creates a duplicate payment.**
This is exactly how Stripe's API behaves, so it's a recognizable, real-world pattern.

> This document is written *before* the code, on purpose. The reasoning below is
> the actual deliverable — the working endpoint is just proof the reasoning holds.

---

## The problem

Networks are unreliable. A client sends `POST /payments`, the payment succeeds on
the server, but the response is lost on the way back (timeout, dropped connection,
client crash). The client has no way to know whether the payment happened, so it
**retries**. Without protection, the retry creates a *second* payment. The customer
is charged twice.

The fix is to let the client attach a unique **idempotency key** to the request.
The server promises: *for a given key, I will perform the operation at most once;
every subsequent request with that key returns the original result.*

The key is generated by the **client** (a UUID per logical operation), not the
server — that's what makes a retry recognizable as the *same* operation rather
than a new one.

---

## The four decisions

These four decisions are the heart of the design. Each one has a trade-off worth
being able to defend out loud.

### 1. The key store and the "insert wins" lock

We keep an `idempotency_record` table with the **key as the primary key**. When a
request arrives, we attempt to `INSERT` a new row with status `IN_PROGRESS`.

The database's **unique constraint on the primary key becomes our lock.** If two
identical requests race, only one `INSERT` can succeed — the other fails with a
unique-constraint violation. No Redis, no `SELECT … FOR UPDATE`, no distributed
lock manager needed for the basic case, because the database *already* guarantees
uniqueness atomically.

```
INSERT INTO idempotency_record (key, status, ...) VALUES (?, 'IN_PROGRESS', ...)
   └── success  → I am the first; I own this key; do the work
   └── conflict → someone else got here first; branch on their row's status (see #3)
```

**Trade-off / likely follow-up:** *When would you reach for a real lock instead?*
- Use the DB unique constraint (this design) when the key store can be **co-located
  with the business data** — same database, same transaction boundary available.
- Reach for `SELECT … FOR UPDATE` or a Postgres **advisory lock** when you need to
  serialize a longer critical section within one DB.
- Reach for a **Redis / distributed lock** only when the work spans **multiple
  services or databases** and no single DB can enforce uniqueness across them.

The insight: don't add a distributed lock until the problem is actually
distributed. The constraint is simpler, has no extra moving parts, and can't drift
out of sync with the data it protects.

### 2. The two-phase commit subtlety (the senior signal)

This is the decision interviewers love when a candidate volunteers it unprompted.

We must **commit the `IN_PROGRESS` row in its own transaction *before* doing the
business work** — not wrap the insert, the work, and the final update in one big
transaction.

**Why.** Under `READ COMMITTED` isolation (Postgres default), a concurrent
transaction cannot see our row until our transaction **commits**. If we wrap
everything in a single transaction:

```
BEGIN
  INSERT idempotency_record (IN_PROGRESS)   -- not visible to anyone else yet
  ... do the payment work ...               -- slow
  UPDATE idempotency_record (COMPLETED)
COMMIT                                       -- only now is the row visible
```

then a second request arriving during "do the work" runs its own `INSERT`,
**doesn't see our uncommitted row**, and... also thinks it's first. Both proceed.
Duplicate payment. The lock silently did nothing.

The correct shape is two phases:

```
Phase A (txn 1):  INSERT IN_PROGRESS; COMMIT      -- claim the key, make it visible
Phase B:          do the payment work
Phase C (txn 2):  UPDATE → COMPLETED + stored response; COMMIT
```

Now the moment we claim the key it is **visible** to everyone else, so a concurrent
request's `INSERT` fails fast and branches correctly.

**Trade-off:** committing first means a row can be left stranded in `IN_PROGRESS`
if the process crashes between Phase A and Phase C. That's acceptable and handled:
such a row blocks duplicates (correct — we don't know if the work happened) and is
eventually swept by expiry (decision #4). We prefer "fails safe toward not
double-charging" over "one tidy transaction."

### 3. The three outcomes when a key already exists

When our `INSERT` fails because the key is taken, we read the existing row and
branch on its state. There are exactly three cases:

| Existing state                         | Meaning                                  | Response |
|----------------------------------------|------------------------------------------|----------|
| `COMPLETED`                            | We already did this work                 | **Replay** the stored response *exactly* — same status code and body. The client cannot tell it was a retry. |
| `IN_PROGRESS`                          | A duplicate is still being processed     | **409 Conflict.** Do **not** redo the work. Client should retry shortly. |
| Key matches, **request body differs**  | Client misuse — same key, different op   | **422 Unprocessable Entity.** |

We detect the third case by storing a **hash of the original request body** on the
record and comparing it to the incoming request's body hash. Same key + different
hash = the client is reusing a key it shouldn't, and we refuse rather than silently
returning a result for a *different* request.

**Why replay must be byte-identical:** the whole point is that a retry is
indistinguishable from the first call. We store the original HTTP status and the
serialized response body, and we return them verbatim — we do **not** re-run the
business logic and hope it produces the same output.

### 4. Expiry

Records have two time bounds, and the README/design should explain *why both
exist*:

- **Keep them long enough to serve replays** — e.g. **24 hours.** A client might
  retry minutes or hours later; within the window, the retry replays cleanly.
- **Expire them after that** — a scheduled cleanup job deletes stale records.
  - so the table doesn't grow **unbounded**, and
  - so keys aren't honored **forever** (a key reused days later is treated as a
    fresh operation, which is the sane default).

A `@Scheduled` task runs periodically and deletes records older than the retention
window. Expiry is the safety valve that also cleans up stranded `IN_PROGRESS` rows
from decision #2.

## Decision flow (the full request path)

```
POST /payments  +  Idempotency-Key header
        │
        ├── header missing? ───────────────────────────► 400 Bad Request
        │
        ▼
  try INSERT idempotency_record(key, IN_PROGRESS, bodyHash)   [txn 1, commit]
        │
        ├── INSERT succeeded (I'm first)
        │         │
        │         ▼
        │   do payment work
        │         │
        │         ▼
        │   UPDATE record → COMPLETED + store(status, body)   [txn 2, commit]
        │         │
        │         ▼
        │   return the freshly created payment (e.g. 201)
        │
        └── INSERT failed (key already exists) → read existing row
                  │
                  ├── bodyHash differs ──────────────────► 422 Unprocessable Entity
                  │
                  ├── status == COMPLETED ───────────────► replay stored response
                  │
                  └── status == IN_PROGRESS ─────────────► 409 Conflict
```

## The test that matters most

The **concurrency test** is the centerpiece. Spin up a thread pool, fire ~20
simultaneous `POST /payments` with the **same** idempotency key, then assert:

1. **Exactly one** `Payment` row was created, and
2. every response was either the replayed success or a `409` — never a second
   distinct payment.

That single test proves the design works under the exact condition it exists to
handle. The happy path proves nothing about idempotency; this proves everything.

  or the whole response envelope? (Start simple: status code + JSON body text.)
